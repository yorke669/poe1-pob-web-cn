# 翻译层（boot.lua T）当前修改与遗留问题

> 更新时间：2026-09-02
> 位置：`packages/driver/boot.lua`（`T()` 翻译层）
> 目标：让 PoB 渲染的英文文本（UI、物品 mod、stat 描述、比较行）在 `DrawString` 上屏前被翻译成中文。

---

## 0. 架构总览

翻译分两条机制，二者共存：

| 机制 | 触发点 | 处理对象 | 说明 |
| --- | --- | --- | --- |
| A. `T()` DrawString hook | 文本**已格式化**（无 `{0}`） | UI 文本 / 物品 affix / 比较行 / 逗号列表 | 见下文 §1 |
| B. StatDescriber 模板 hook | `LoadModule("Data/StatDescriptions/*")` 加载时 | 含 `{0}` 占位符的模板 | 递归遍历 scope table，对 `text` 字段做「归一化→查表→还原」 |

机制 B 是机制 A 之前就加的「模板层」，处理 `Adds {0} to {1} Physical Damage` 这类。
机制 A 是 `T()` 主函数，处理一切经过 `DrawString` 的**已解析**字符串。

---

## 1. 机制 A：`T(text)` 当前实现

入口（`boot.lua:421`）先做颜色码剥离：

- `splitLeadingEscapes(text)`（:240）：保留 `^xRRGGBB` / `^d` 等前缀，翻译后原样接回，避免中文变黑/灰。
- `stripEscapes(key)`（:264）：查表前去除所有 `^%d` 与 `^xRRGGBB`。

随后按以下**顺序**回退（任一层命中即返回）：

1. **精确匹配** `translateTable[key]`（:434）
2. **冒号标签前缀** `^(.-):`（:442）：`Armour: 960` → 切出 `Armour` 命中 → `护甲: 960`。覆盖所有数值类标签。
3. **逗号分隔列表**（:451）：`Spell, AoE, Fire, Duration` / `Requires Level 70, 68 Dex, 98 Int`，逐段翻译；段内带数字时先 `resolveToTemplate` 归一化再查模板。
4. **模板路径**（:487，条件 `key:find("[%d%%%(]")`）：见 §2。
5. **比较行**（:548）：`+667.5 Average Hit (+133.5%)` 等分出数值与 label，翻译 label 后接回。
6. **终极 MISS**（:578）：`[translate] MISS key=...`（仅 debug）。

辅助表：

- `translateTableLower`（:202）：`translateTable` 的小写镜像，用于 PoB 把物品行渲染成 **ALL CAPS** 而语料是 Title Case 的情况（大小写无关匹配）。
- `fuzzyLabelTable`（:226）：对含 `()` 或 `:` 的 key 做 `normLabel` 归一（去标点/空白）后建表，给比较行 label 兜底。

---

## 2. 模板路径详解（`resolveToTemplate` + 多级回退）

`resolveToTemplate(text)`（:288）把已解析文本**逆归一化**回模板：

- 第一步 `%b()`：把范围 `(80-120)` → 占位符 `@VA@`，记录 value。
- 第二步 `([%+%-]?%d+%.?%d*)`：其余数字 → 占位符（用**字母标签** `@VA@` 而非数字，避免二次 gsub 把标签内数字又吃掉）。
- 第三步：字母标签 → `{0}` / `{1}` 形式。
- 返回 `templ` 与原 `values`，命中后 `values[i+1]` 回填 `{i}`。

命中后的回退顺序（:487-541）：

1. **去除尾部 `(...)` 占位**（:494）：`ItemTools.lua:370` 给未解析的 mod 追加 `(Not supported in PoB yet)`，整行喂给 `T()`。把尾部 `(...)` 剥掉尝试命中真实 stat，命中后把原 suffix 接回，提示语保留。
2. **带符号回退**（:511）：`+(30-40) to Intelligence` 先整串试，未中则剥掉 `+`/`-` 试 `{0} to Intelligence`，命中后把符号重新前缀，保留 `+`。
3. **分词兜底** `translateBySegmentation(templ)`（:523）：见 §3。

翻译成功后 `result` = 模板回填数值 + 原 suffix（:532-539）。

---

## 3. 分词兜底 `translateBySegmentation`（:365）

解决语料**断行污染**：GGG 原文换行的 stat 被 PoeCharm 拆成两个 key——前半句（带 `{0}`）+ 小写开头的尾部（如 `containing Corrupted Magic Jewels`）。PoB 渲染成一整行，合并形式永远查不到。

做法：**最长匹配分词**。

- 按空格切词，从最长片段到最短试，每段查 `translateTable` / `translateTableLower`。
- **严格约束**（:383）：只有首段可以是独立短语；后续片段必须 `^%l`（小写开头），这是「被拆出的尾部」的标志。去掉该约束会让无关 key 串起来（曾把 `Maximum 1 Stage` 翻成 `最大值1 阶`）。
- `fixPolarity(templ, tr)`（:343）：强制译文 `提高/降低` 与原文 `increased/reduced` 一致（同一尾部 key 同时服务两种变体，否则会反向）。
- **高亮词吞并**（:395）：PoB 的 stat describer 把高亮词（`Magic`/`Jewels`）单独 `DrawString`，背景行在最后一个高亮词前被截断。允许把下一个 `^%u` 大写词吞进来一起查，使 `containing Corrupted Magic` 能命中 `containing Corrupted Magic Jewels`。
- `segmentCache`（:361）：miss 记 `false`，重复 miss 跳过 O(n²) 扫描。
- **只全中才返回**（:412 `#parts > 1` 且 `ok`），绝不半翻。

## 4. 调试开关

`translateDebug`（:154）由 `POE_TRANSLATE_DEBUG=1` 或 `_G.translateDebug=true` 开启，**默认 false**（之前一次「日志没打印」就是被覆盖成 false）。

开启后打印：

- 逐文件加载汇总（:194）
- `T key=`（:427）：任何「像 mod 行」的 key（含数字/百分号/括号，或命中 jewel/corrupted/recovered/stunning/damage taken/not supported 任一关键词）都会打印**原始**字符串，直接看到 PoB 喂给 `T()` 的是什么。
- `TEMPLATE key -> templ -> result`（命中）/`TEMPLATE MISS key= templ=`（未命中，:528）：模板路径对**每一条** mod 行都打印原始 key、归一化后的 `templ`、以及是否命中。这样无需按关键词过滤即可看清「语料有但没翻」的真实差异（大小写 / 数字格式 / 缺词）。
- `LIST`、`COMPARE`、`MISS`、`STAT` 等。

## 6. 遗留问题（待诊断 / 待修复）

### 6.1 血痕赤红珠宝 unsupported mod 未翻译 ⚠️

现象：物品**血痕赤红珠宝（Bloodstained Crimson Jewel）** 的隐式 mod：

```
(20-30)% of Damage taken from Stunning Hits is Recovered as Life (Not supported in PoB yet)
```

正文**不翻译**（显示英文），而该 stat 的精确条目已在语料：

```
statDescriptions.csv:28410
"{0}% of Damage taken from Stunning Hits is Recovered as Life" , "所受晕眩击中生命的 {0}% 回复为生命"
```

已知事实：

- 这是 **unsupported mod**（`modLine.extra` 为真，`Item.lua` 中 `modLine.extra = extra`），因为 PoB 没实现该 stat 解析。
- 正文来自 `modLine.line`（GGG 原版 stat 文本，`ItemTools.lua:370` 追加 `(Not supported in PoB yet)`）。
- 用户反馈 `(Not supported...)` 是**单独**渲染的（不是和正文同一次 `DrawString`）。

矛盾点：按当前模板路径逻辑，正文 `(20-30)% of Damage taken from Stunning Hits is Recovered as Life` 应当能经 `resolveToTemplate` 命中文语料——但它没翻。说明**真正喂给 `T()` 的字符串与语料存在微妙差异**（大小写 / 数字格式 / 某字符），仅凭读代码无法确定。

已采取的措施（诊断，非修复）：

- 把 `T()` 入口调试从「按关键词过滤」改为**捕获所有 mod 行**（含数字/百分号/括号即打印原始 `key=`，:427），模板路径对所有 key 打印 `TEMPLATE key -> templ -> result` 或 `TEMPLATE MISS key= templ=`（:528）。开启 `POE_TRANSLATE_DEBUG=1` 后悬停该珠宝，即可在 Console 看到 PoB 实际传入的**完整原始字符串**与归一化后的模板，据此定位差异（而不是凭猜测）。
- `translateDebug` 此前一度被 `do` 块无条件覆盖成 `false`（死代码），导致前几轮「日志没打印」——已修正为 `local translateDebug = false`（:154），现受 `POE_TRANSLATE_DEBUG=1` 正确控制。

待用户执行（已上传 boot.lua，md5 `6fd3012476e3bae69a5f393773a13ce8`）：

```bash
cd /opt/poe/poe1-pob-web
export EMSDK_PYTHON=$(which python3)
export POE_TRANSLATE_DEBUG=1
./代码阅读/scripts/driver-build.sh --kind debug
# 重启 dev 时也要带 POE_TRANSLATE_DEBUG=1（os.getenv 在 wasm 加载时读取）
POE_TRANSLATE_DEBUG=1 mise run driver:dev --game poe1 --version v2.67.2
```

浏览器 Cmd+Shift+R，悬停血痕赤红珠宝，把 Console 里的 `[translate] T key=` / `[translate] TEMPLATE MISS key= templ=` 发回，据此定位差异后用**规律**（而非特例）修复。

## 7. 浮华珠宝（The Adorned）翻译问题完整解决历程

> 对象：浮华赤红珠宝（The Adorned）的隐式 mod
> `(0-100)% increased Effect of Jewel Socket Passive Skills containing Corrupted Magic Jewels`
> （及 reduced / Rare 变体）。这是最典型、也最曲折的一条未翻译词条。

### 7.1 走过的弯路（已被推翻）

- **早期硬编码方案（已废弃）**：曾加 `specialStatTemplates`（把整条 `... CONTAINING CORRUPTED MAGIC JEWELS` 硬编码成中文）+ `jewelSuffixTable`（`Magic Jewels`→`魔法的珠宝`）。
  - 但 PoB 实际渲染是把这条 mod **按 `Jewels` 切分**——前缀 `(0-100)% ... CONTAINING CORRUPTED MAGIC`（ALL CAPS）作为探索 key 反复减词调 `T()`，只剩 `Jewels` 作为独立 key。硬编码前缀永远对不上真实传入片段，且**会去给 `WrapString` 逐词测宽的副产物配翻译**（那些 `Passive` / `Passive Skills` / `... containing` 递增前缀根本不是渲染路径）。
- **用户明确否决**：不要自己加特殊处理，全部寻找规律匹配。

### 7.2 根因 A：语料「断行污染」（机制层面，已用规律修复）

- 上游 `Data/StatDescriptions/stat_descriptions.lua:187842` 的 text 是**单行完整句**（无 `\n`）。
- PoeCharm 语料按 GGG 原始**行**生成，一条英文换行的 stat 被拆成两个 key：
  1. 前半句（带 `{0}` 占位符）：`{0}% increased Effect of Jewel Socket Passive Skills`
  2. **小写开头的尾部 key**：`containing Corrupted Magic Jewels`（语料共 **276 条**这类小写开头 key）
- PoB 渲染时拼成一行，合并形式 `... Passive Skills containing Corrupted Magic Jewels` 永远不在表里 → 整句 MISS 显示英文。
- **通用解法（已落地，无硬编码）**：`translateBySegmentation(templ)` 最长匹配分词（见 §3），严格约束「后续片段必须小写开头」，并用 `fixPolarity` 修正 increased/reduced 共用尾部 key 导致的语义翻转。模拟验证：目标句精确命中、零误伤（非 strict 模式会把 `Maximum 1 Stage` 译成 `最大值1 阶`，证明严格约束必要）。

### 7.3 根因 B：WrapString hook 从未安装（挂载时机，已修复）

- 即使有了分词兜底，浮华珠宝依旧翻不出——因为长行被 `Tooltip.lua:107` 的 `main:WrapString(line)` 拆成片段，**每片段独立 `DrawString`**，`T()` 只拿到碎片（如只剩 `Magic` 命中 `GUI.lua:54 ["Magic"]="魔法的"`），整句从未在整行层面翻译。
- **真根因**：`boot.lua` 在 `dofile("Launch.lua")` 之后立即取 `mainObject.main`，但 `Launch.lua:71` 的 `self.main = PLoadModule("Modules/Main")` 是在 `launch:OnInit()`（driver 主循环里、boot.lua 跑完之后）才执行。那时 `mainObject.main` 恒为 nil → 包装器**一次都没装上**。
- **修复**：把挂载逻辑抽成 `installWrapStringHook(mainInst)`，在 **`mainObject["OnInit"]` 包装函数的 `onInit(self)` 之后**调用——此时 `self.main` 已由 Launch 创建。这样长行先在整行层面翻译再折行。
- **副作用**：WrapString hook 一旦生效，**所有长文本（gem description、flavour text、item mod 行、技能描述）都会在整行层面先翻译**，一次性修复大量此前「只翻了单词、整句英文」的显示。

### 7.4 最终结论

浮华珠宝这条最终能翻，是**两层修复叠加**的结果：

1. **分词兜底（规律匹配）** 解决语料断行污染（§3 / 7.2）；
2. **WrapString hook 正确挂载** 保证整行文本到达 `T()`（7.3）。

二者缺一不可：只有分词兜底时，长行被拆碎，`T()` 根本拿不到完整句；只有 hook 没有分词兜底时，完整句到达 `T()` 但仍因合并形式不在语料而 MISS。
